BACKEND FINDINGS — "Manual Fix" step generation, admin vs user (answering your 3 questions)

Investigated by reading both handlers side by side (adminregister.views.FixVulnerabilityCreateAPIView
and userregister.views.UserFixVulnerabilityCreateAPIView) plus FixVulnerabilityStepsAPIView, and
confirming live against a real report.

1) Does the admin create endpoint trigger the same step-generation process as the user one?
   Neither one triggers ANY step generation. Both "create" handlers just insert a lightweight
   tracking document (report_id, host_name, plugin_name, assigned_team, etc. — no steps) into the
   same `fix_vulnerabilities` collection. The actual step content ("Remediation Sub-Tasks") always
   comes from vulnerability_cards.mitigation_table, which is generated ONCE per vulnerability by a
   background job (_auto_generate_cards_bg) that runs right after the report is UPLOADED — this is
   completely independent of whether/when anyone calls the "create fix" endpoint, on either side.

2) Is there a delay between creation and steps being ready? How long, for your retry window?
   No delay tied to "create" itself — verified live: POST create → GET steps returned a full,
   populated 10-step plan in well under a second. The real delay is tied to UPLOAD, not create:
   card generation makes a real AI call per vulnerability and can take anywhere from ~45 seconds
   (small reports) to several minutes for large ones. If "Manual Fix" is opened for a vulnerability
   before ITS card has been generated yet, steps genuinely don't exist yet — regardless of which
   side (admin or user) is asking.

3) Are the admin-created and user-created records the same document, or two separate ones?
   Same document, confirmed by code. Both handlers query the identical `fix_vulnerabilities`
   collection with the identical duplicate-check key (report_id, host_name, plugin_name) before
   inserting — whichever side creates first "wins" (201), and the other side's later create call
   finds that same record and returns it (200), never creating a second one. This is not the
   explanation for what you saw.

ROOT CAUSE OF WHAT YOU OBSERVED
Not an admin-vs-user difference at all. Most likely explanation: you tried admin first, right
after upload, before that specific vulnerability's card had finished generating in the
background — got "Fix Not Started". By the time you tried the same vulnerability from the user
side, more real time had passed since upload, so the background job had caught up and the card
(with its steps) now existed — which is also why going back to admin then worked. The user path
isn't doing anything special; it just happened to be tried later.

RECOMMENDED FIX (frontend-side, no backend change needed for this)
Instead of blindly retrying create+steps every 4s for ~30s, poll the existing card-generation
status endpoint and only surface "Manual Fix" as ready once it reports completion:

  GET /api/admin/upload_report/upload/<report_id>/status/   (admin-side, already exists)

Response includes:
  {
    "cards_generation_complete": true/false,
    "cards_generated": <int>,
    "cards_total": <int>,
    "remaining_seconds": <int>,       // ETA if not complete yet
    "remaining_time_text": "e.g. 45 sec",
    ...
  }

While cards_generation_complete is false, show a "still generating your remediation plan —
about Xs left" state instead of "Fix Not Started" (which reads as a permanent failure, not a
transient one). Once true, call create + steps as you already do.

IMPORTANT LIMITATION: this status endpoint is ADMIN-ONLY right now — it checks the report's
owning admin directly against request.user.id, so a team-member (user-side) caller gets 403.
There is currently no equivalent for the user/team-member side. Two options:
  (a) Keep your existing retry-loop specifically for the user-side flow (it already works,
      just not as efficient/informative as polling would be), or
  (b) Ask the backend for a small addition — a user-side version of this same status endpoint,
      scoped to the team member's linked admin instead of a direct admin.id match (same pattern
      every other user-side endpoint in this API already follows). This has NOT been built yet;
      flag it back if you want it — it's a small, low-risk addition, just not done automatically
      since your retry-loop already works today.
