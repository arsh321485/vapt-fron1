Backend Prompt: Build POST /api/admin/billing/checkout/custom/

Context: 
The VAPTFix frontend's "Custom" pricing plan (>250 assets) has a "Confirm & pay"
screen that already calls this endpoint, but it currently returns 404 — it doesn't
exist on the backend yet. This blocks all Custom-tier checkouts (users see
"Checkout failed, status code 404" right after their sales lead is successfully
submitted).

What already works (don't touch):
- POST /api/admin/billing/leads/custom/ — already implemented, returns
  {"detail": "Request submitted. Our sales team will reach out."}. This just logs
  a sales lead; it does not create a subscription or charge anything.

What needs to be built:
A new endpoint that mirrors POST /api/admin/billing/checkout/premium/ exactly
(same auth, same Stripe Checkout Session pattern, same response shape), but for
the Custom tier.

Endpoint
--------
POST /api/admin/billing/checkout/custom/
Auth: same as /checkout/premium/ (admin session/bearer token)

Request body
------------
{ "asset_count": 342 }

- asset_count is required, integer, must be > 250 (Custom tier only applies above
  the Premium ceiling — reject with 400 if <= 250, pointing the client to
  /checkout/premium/ instead).

Pricing (frontend's current assumption — confirm/adjust as needed)
--------------------------------------------------------------------
- Rate: $1.25 per IP per month, billed as one annual charge (Custom is
  Annual-only, no monthly/semi-annual option).
- amount_due = asset_count * 1.25 * 12
- Currency: usd
- This mirrors Premium's Annual cycle rate exactly (see checkout/premium/'s
  billing_cycle=annual pricing) — same formula, just uncapped since Custom has no
  250-asset ceiling.

Response body (must match this shape — frontend already expects it)
---------------------------------------------------------------------
{
  "checkout_url": "https://checkout.stripe.com/...",
  "session_id": "cs_...",
  "amount_due": "5130.00"
}

Behavior
--------
1. Validate asset_count > 250 (400 otherwise, with an error message in detail).
2. Create a Stripe Checkout Session for the calculated amount_due (same session
   mode/config as /checkout/premium/ uses — subscription with annual recurring
   price, since Custom should flow through the same subscription lifecycle as
   Premium).
3. Store the pending session/subscription with plan = "custom" so it's tagged
   correctly.
4. Return checkout_url, session_id, amount_due as above. Frontend immediately
   redirects the browser to checkout_url.

Downstream dependency — must also update
-------------------------------------------
GET /api/admin/billing/checkout/confirm/?session_id=... (already built for
Premium) is called after Stripe redirects the user back to /billing/success. It
must recognize and correctly activate plan="custom" sessions/subscriptions the
same way it does for "premium" — same BillingSubscription response shape (plan,
mode, billing_cycle, price_per_ip, amount_due, status, etc.), just with
plan: "custom". If this endpoint currently hardcodes or only recognizes
"premium", it needs to be generalized. Same applies to
GET /api/admin/billing/subscription/me/ and
POST /api/admin/billing/subscription/cancel/ / sync-assets/ — they must handle
plan="custom" subscriptions without special-casing failures.

Error handling convention (match existing endpoints)
--------------------------------------------------------
On error, return a JSON body with a detail (string) or field-level errors (e.g.
{"asset_count": ["..."]}) — the frontend's billingErrorMessage() helper already
parses both shapes.
