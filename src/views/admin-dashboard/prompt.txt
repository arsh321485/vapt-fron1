Admin Onboarding Flow — Frontend Implementation Spec
Background
Every admin now goes through 3 states before they can see their real dashboard:

no_report — Super Admin hasn't uploaded a vulnerability scan report for this admin yet.
needs_risk_criteria — a report exists, but the admin hasn't set their Risk Criteria (per-severity SLA/fix deadlines) yet.
ready — both exist → show the normal dashboard.
This already works end-to-end on the Slack side. This spec is for building the equivalent on the website.

1. Check onboarding state
GET /api/admin/admindashboard/dashboard/report-status/
Auth: Authorization: Bearer <admin JWT> (same token used for every other admin API call)

Call this right after login, and again after any action that might change state.

Response shape (all 3 states share the same fields)

{
  "state": "no_report" | "needs_risk_criteria" | "ready",
  "has_report": false,
  "has_risk_criteria": false,
  "show_dashboard": false,
  "admin_id": "5d0a5746-...",
  "admin_email": "admin@example.com",
  "report_id": null,
  "message": "No report uploaded yet. Please wait for Super Admin to upload a report."
}
state is the field to branch UI on — the booleans are kept for backward compatibility.

What to show per state
state	Screen
no_report	Waiting screen: "Your Super Admin needs to upload your first vulnerability scan report before you can get started. We'll let you know the moment it's ready." No dashboard nav, no data.
needs_risk_criteria	Risk Criteria setup form (below) — block the rest of the dashboard until submitted.
ready	Normal dashboard — existing behavior, nothing new.
Polling
The no_report → needs_risk_criteria transition is outside the admin's control (Super Admin uploads whenever they do). Poll this endpoint every 30–60s on the waiting screen and transition automatically when state changes — no manual refresh. Once in needs_risk_criteria, no polling needed (that step is user-driven).

2. Risk Criteria setup form
Shown only when state === "needs_risk_criteria". Reuses the existing create endpoint — nothing new here.

POST /api/admin/risk_criteria/add-risk/

Request body (all 4 fields free text, not numbers):


{ "critical": "1 day", "high": "3 days", "medium": "1 week", "low": "2 weeks" }
Backend parses formats like "3", "day 3", "1 week", "1 week 2 days". Show 4 required text inputs (Critical/High/Medium/Low) — reuse the same field components if a "edit risk criteria" form already exists elsewhere.

Success (201) returns the saved record. On success: re-call the report-status endpoint — it'll now return state: "ready" — and route into the dashboard.

Summary
Purpose	Method	URL	New or existing?
Check onboarding state	GET	/api/admin/admindashboard/dashboard/report-status/	Existing, extended — used to only return has_report; now also returns state + has_risk_criteria.
Submit risk criteria	POST	/api/admin/risk_criteria/add-risk/	Existing, unchanged.
No new endpoints were created — only the report-status response gained two fields, so any old code reading just has_report/show_dashboard still works unchanged.
