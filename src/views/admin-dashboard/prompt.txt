Frontend ko koi naya endpoint ya card_id-resolution nahi chahiye — jo response manual steps (mitigation_table) ke liye already use ho raha hai (VulnerabilityCardDetailView — GET /api/admin/upload_report/vulnerability-cards/<card_id>/, aur list wala VulnerabilityCardListView), usi document me card_id aur automation_card already hain, koi extra call nahi lagegi.

Maine sirf ek zaroori fix add kiya (dono jagah):

VulnerabilityCardDetailView aur VulnerabilityCardListView — ab automation_card return karte waqt, agar us report ka admin Freemium hai to fix_script/verify_script khaali kar dete hain (baaki fields — status, description, considerations — dikhte hain) + ek "premium_required": true/false flag bhi bhej dete hain, taaki frontend "Upgrade to Premium" UI dikha sake. Ye wahi rule hai jo curated automation-scripts feature me pehle se hai — Freemium ko script CONTENT kabhi bhi seedha nahi milna chahiye.
Frontend ko batao: card.automation_card ko usi response se read karo jaha card.mitigation_table already read kar rahe ho — dono ek hi object me hain. card.automation_card.premium_required check karke lock UI dikhao, card.automation_card.automation_status (full/partial/not_possible) se 3-state UI, aur fix_script/verify_script seedha wahi se milega (Premium ke liye).

Frontend ke liye instruction
card.card_id — id jo pehle se available hai, koi nayi field nahi.
card.automation_card.automation_status — "full" / "partial" / "not_possible" → 3-state UI.
card.automation_card.premium_required — true ho to lock/upgrade UI dikhao, script fields khaali honge.
card.automation_card.reason_not_possible — sirf jab automation_status = "not_possible" ho, wahi message dikhana.
Fix/Verify script download button ke liye ye fix_script/verify_script text ko seedha file bana kar bhi de sakte ho (Premium case me already text mil raha hai yahi response me), ya mera pehle wala dedicated download endpoint (/api/user/automation-scripts/ai/<card_id>/download/?type=fix) bhi use kar sakte ho member side ke liye.
